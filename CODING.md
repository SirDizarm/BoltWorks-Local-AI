# Work on code

Select **Work on code** from the workspace selector. Choose and lock a text GGUF in the **Chat** slot, choose your source project folder, describe a specific change, and press **Run coding task**. Choose **Any language**, **C# / .NET**, **Minecraft mod (Java)** or **Legacy code / assembly** for project-specific guidance. The legacy preset works with source/disassembly exports or approved commands against already-installed analysis tools; it does not install REA or add XP compatibility. Existing model assignments work without conversion. A code-trained instruction model is preferable; small general models may need smaller tasks or may fail to follow the tool protocol.

Inference is local and offline, using the supplied llama.cpp runtime and your GGUF. No cloud API, Microsoft account, email login or online inference is used; a local Windows user account works. The presets tell the model to use installed tools and local documentation, preserve project versions and report missing dependencies. This instruction is not a network firewall; inspect requested commands before allowing them.

Before moving to a disconnected laptop, copy the entire application distribution and model files, and prepare the build environment:

- **C# / .NET:** install the SDK or .NET Framework build tools required by the project. Restore required NuGet packages while connected and preserve their cache and project assets. Offline tasks prefer `dotnet build --no-restore` and `dotnet test --no-restore` where applicable.
- **Minecraft Java mods:** choose the exact Minecraft version and Forge, NeoForge or Fabric loader. Prepare its starter project, compatible JDK, Gradle distribution and dependencies while connected. Run a successful build beforehand, then test `gradlew.bat --offline --no-daemon build`. Copy the project and the required caches to the laptop with the appropriate paths. A Gradle wrapper alone does not contain its distribution or dependency cache.
- **Other languages:** provide the compiler/interpreter, build tools, dependencies and any useful local documentation. Source editing itself does not require these tools, but compilation and tests do.

The Minecraft preset reads existing Gradle files and mod metadata before editing and tells the model not to mix loader APIs. For a new mod, include the Minecraft version and loader in your task or start from a prepared template. These presets guide the same file tools; they do not bundle Java, Gradle, Minecraft, .NET SDKs or package caches.

The model can list directories, read source files in pages, find text within a file, create new files and replace an exact unique passage. These are real disk operations. Edits require a fresh read and stop if the file changed since that read. Files are saved immediately. Stop cancels inference or the running command; it does not undo completed edits. Each run starts with a fresh model conversation and has a configurable limit of 1–60 tool steps.

For build, test or project-wide search commands, the app shows the exact PowerShell command and working directory. **Run command** authorizes that command; **Deny** returns the refusal to the model. Commands run with your Windows user permissions and are not confined to the project folder. They time out after two minutes, and stopping the job terminates the command process tree. The model unloads before an approved command to free RAM, then reloads when the task continues. The output tail and exit code are returned to the model and shown in the log. No command can run just because the model prints a success message.

File tools accept only paths within the selected folder and reject junctions/symlinks, alternate streams, parent traversal, Git metadata, common dependency folders, and `.env` files. They support UTF-8 text files up to 512 KB, preserve an existing UTF-8 BOM, and preserve unchanged text and line endings. There is no delete tool. These checks protect ordinary file operations; the application is not an operating-system sandbox.

Every run saves the task, raw model actions, tool results and edit backups under `%LOCALAPPDATA%\BoltWorks\LlamaLite\code-jobs`. The exact job path appears in the status line; **Job files** opens it. Each edit has a JSON record containing the original absolute path, whether the file was newly created, and its `.before` backup filename. To undo an edit, stop the task, inspect the record, and copy the corresponding `.before` file back to its recorded path. Multiple edits have separate backups; restore in reverse order to undo a whole run. Newly created files have no original backup. Commands may modify files without these backups, so use version control for larger tasks.

In Normal memory mode the coding workspace uses a 16,384-token context and up to 3,072 reply tokens per step. Low RAM and Disk-backed CPU modes use 4096 context tokens and up to 1024 reply tokens. Coding measures the actual formatted prompt with the model tokenizer and shortens older exchanges/tool excerpts as needed while retaining the task. See MEMORY-AND-LEGACY.md. CPU/CUDA selection is shared with the rest of the app. Only one AI workspace runs at a time. Older source excerpts age out of the conversation; the model retains a bounded action record and can reread files. Three consecutive tool errors stop the run. The final model summary is labelled as such and accompanied by application-counted file edits and commands; use the actual tool results and your project's tests to assess its work.

Developer checks: build with `build.ps1`, then run `BoltWorks-Local-AI.exe --code-test NEW_OUTPUT_FOLDER [MODEL_GGUF]`. Without a model this exercises file boundaries, edit conflicts/backups, command execution/cancellation and the agent loop. Supplying a model also tests a real read/edit task against a temporary C# source file, then independently compiles and executes it using the installed .NET Framework compiler. `--render-preview OUTPUT_PNG 6` renders the coding workspace.

Validation for 0.6.3: file/command tests and existing model-slot/integration checks passed; the coding workspace was rendered and inspected. The installed Qwen3.5-9B Q5_K_M model read, corrected and reread a small C# program through the real tools. The corrected program was then compiled and executed through the final command runner, producing `Hello` with exit code 0. A separate lifecycle check verified compilation after unloading a local inference model. The 0.6B model did not reliably complete the edit and could claim a change it had not made; this is why application action counts are separate from model summaries. A full Minecraft mod build and larger software projects have not been validated.
